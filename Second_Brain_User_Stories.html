Second Brain AI Assistant

Detailed delivery backlog · Derived from Technical Requirements Document v1.2 · Project code: SB

This backlog converts the technical requirements into independently deliverable user stories. Each story is intended to be refined into implementation tasks during sprint planning. “Done” means all stated acceptance criteria pass in the target environment.

Backlog conventions

FieldMeaning
StoryThe user or operational outcome to deliver.
Acceptance criteriaObservable conditions required before the story is complete.
DependenciesCapabilities that must be available or agreed before implementation.

Epic A — Platform Foundation

SB-1 Establish the monorepo and shared contracts

Story: As an engineering team, we need a predictable repository structure so web, API, workers, agent capabilities, and shared schemas can evolve together.

Acceptance criteria

  • The repository contains apps for web, API, and worker plus packages for agent, RAG, memory, graph, MCP, and shared contracts.
  • Shared request, response, error, and domain schemas are version-controlled and importable by every relevant service.
  • Local setup, test, lint, and build commands are documented and run from a clean checkout.

Dependencies: Language/package-manager choices and CI baseline.

SB-2 Provide a reproducible local environment

Story: As a developer, I want to start the required local services consistently so I can develop and test the platform without manual infrastructure setup.

Acceptance criteria

  • Docker Compose starts web, API, worker, Redis, PostgreSQL, Qdrant, Neo4j, and MCP server with documented commands.
  • Configuration is supplied through documented environment variables; secrets are not committed.
  • A smoke check confirms health for each required service and clear failure messages identify unavailable dependencies.

Dependencies: SB-1; local container images and configuration contract.

SB-3 Define the domain error and API versioning standard

Story: As a frontend developer, I need stable API errors and versioned routes so the UI can handle failures without provider-specific logic.

Acceptance criteria

  • All public endpoints use the /api/v1 prefix.
  • Error responses follow one documented envelope with machine-readable code, safe message, request/trace ID, and optional field errors.
  • Validation, authentication, authorization, conflict, and upstream failures map consistently to documented HTTP statuses.

Dependencies: SB-1.

SB-4 Manage runtime configuration and secrets

Story: As an operator, I need configuration and credentials managed safely across environments so deployments are repeatable and secrets do not leak.

Acceptance criteria

  • Configuration is validated at startup and fails fast when required values are missing or malformed.
  • Secrets are loaded from an approved secret mechanism, masked in logs, and never returned by health or debug endpoints.
  • Environment-specific configuration, rotation procedure, and ownership are documented.

Dependencies: SB-2; selected secret-management approach.

SB-5 Create database migrations and core persistence

Story: As a backend service, I need an authoritative relational data model so user, document, conversation, integration, job, workflow, and audit records are durable.

Acceptance criteria

  • Migrations create the core PostgreSQL aggregates listed in the TRD, including users, sessions, documents, document versions/chunks, conversations/messages, integrations, jobs, tool invocations, audits, and workflow traces.
  • Foreign keys, indexes, timestamps, and user-scope fields are defined for expected queries.
  • Migrations are repeatable in CI and can upgrade an empty database without manual SQL.

Dependencies: SB-1, SB-2.

Epic B — Identity, Sessions, and Access Control

SB-6 Authenticate a user

Story: As a user, I want to sign in securely so my knowledge and connected accounts are accessible only to me.

Acceptance criteria

  • Login creates a secure session and GET /api/v1/me returns the authenticated user profile.
  • Invalid credentials and expired sessions return the standard error envelope without account enumeration.
  • Session cookies/tokens use secure transport and expiration settings appropriate to the selected auth design.

Dependencies: SB-3, SB-5; approved identity provider or credential policy.

SB-7 End an authenticated session

Story: As a user, I want to log out so access from a device can be ended deliberately.

Acceptance criteria

  • POST /api/v1/auth/logout invalidates the active session/token according to the authentication design.
  • Subsequent protected calls are rejected and the web application returns to the signed-out state.
  • Logout activity is auditable without recording sensitive token material.

Dependencies: SB-6, SB-38.

SB-8 Enforce user-scoped data access

Story: As a user, I need all of my documents, memories, conversations, vectors, graph records, and integrations isolated from other users.

Acceptance criteria

  • Every repository and retrieval path derives user scope from authenticated context rather than a client-supplied user ID.
  • Cross-user reads, writes, updates, deletes, vector retrieval, and graph traversal are rejected or yield no data.
  • Automated authorization tests cover representative resources across all stores.

Dependencies: SB-5, SB-6; store-specific filtering design.

Epic C — Web Application Shell

SB-9 Deliver the React application shell

Story: As a user, I want a consistent application shell so I can navigate Second Brain confidently.

Acceptance criteria

  • The React/Vite/Ant Design application provides authenticated layout, navigation, responsive loading states, and error boundaries.
  • Routes exist for Chat, Documents, Memories, Graph, Integrations, Jobs, Audit, and Settings.
  • Feature modules follow the approved folder structure and do not import backend storage/provider clients directly.

Dependencies: SB-1, SB-6.

SB-10 Standardize client state and API access

Story: As a frontend developer, I need clear state ownership so cached server data and UI-only state stay maintainable.

Acceptance criteria

  • TanStack Query owns fetching, caching, mutations, invalidation, and retry presentation for server data.
  • Redux is limited to documented cross-feature client state; component-local state remains local by default.
  • A shared API client handles auth, trace IDs, errors, pagination, and response normalization.

Dependencies: SB-3, SB-9.

SB-11 Show operational feedback in the interface

Story: As a user, I want clear loading, success, empty, and failure feedback so I understand the state of my requests and jobs.

Acceptance criteria

  • All primary screens display deliberate loading, empty, permission, and error states.
  • Async work exposes status and a safe retry path where retry is permitted.
  • User-facing errors are actionable and do not expose internal infrastructure or secrets.

Dependencies: SB-3, SB-9, SB-36.

Epic D — Document Lifecycle and Ingestion

SB-12 Upload a supported document

Story: As a user, I want to upload PDF, DOCX, TXT, Markdown, and CSV files so I can add personal knowledge to Second Brain.

Acceptance criteria

  • POST /api/v1/documents validates type, size, authenticated ownership, and duplicate-handling policy.
  • The original file is stored in object storage and a document metadata record is created before background processing starts.
  • The API returns a document ID and initial lifecycle status without waiting for ingestion to finish.

Dependencies: SB-2, SB-5, SB-8; file-size and malware-scanning policy.

SB-13 Browse and inspect documents

Story: As a user, I want to list and inspect my documents so I can understand what is indexed and why.

Acceptance criteria

  • Document list supports user-scoped search, filter, pagination, and lifecycle status.
  • Document details show metadata, source preview/access, ingestion status, chunk/provenance summary, and errors where applicable.
  • Only the owner can retrieve a document or its details.

Dependencies: SB-8, SB-12.

SB-14 Queue document ingestion

Story: As the platform, I need uploads processed asynchronously so long-running work does not block the API.

Acceptance criteria

  • Creating a document queues an idempotent ingestion job in Redis and records QUEUED/PROCESSING/COMPLETED/ERROR/DEAD_LETTER states.
  • Repeated delivery of the same job cannot create duplicate active versions or inconsistent ready status.
  • The UI and API expose current status and a safe reingestion operation.

Dependencies: SB-12, SB-35.

SB-15 Parse and normalize document content

Story: As a retrieval pipeline, I need clean normalized content so supported files can be indexed consistently.

Acceptance criteria

  • Workers extract text and available page/section metadata from each supported type.
  • Parser failures preserve the original document, record a safe diagnostic, and set a terminal/retryable status according to policy.
  • Unsupported image/OCR inputs are rejected or clearly marked as unsupported until OCR is enabled.

Dependencies: SB-14; approved parser library and OCR boundary.

SB-16 Chunk documents deterministically

Story: As the RAG service, I need stable chunks with provenance so retrieval is reproducible and citations are trustworthy.

Acceptance criteria

  • Chunking produces chunk ID, document ID, page/section when available, index, ingestion version, content hash, and text.
  • Reingesting unchanged content with the same version produces stable chunk identity or a documented equivalence rule.
  • Chunk boundaries, overlap, token limits, and versioning are configured and covered by tests.

Dependencies: SB-15.

SB-17 Index document embeddings in Qdrant

Story: As the platform, I need semantic vectors stored with filtering metadata so users can retrieve relevant evidence safely.

Acceptance criteria

  • Every indexed vector contains user ID, document ID, chunk ID, page, section, tags, and ingestion version payload fields.
  • Vectors can be filtered by authenticated user, document, tag, date range, and owner scope.
  • Index write failures leave document status non-READY and are retried or reported consistently.

Dependencies: SB-8, SB-16; embedding-provider abstraction.

SB-18 Manage document deletion and reingestion

Story: As a user, I want to remove or reindex a document so stale or unwanted knowledge no longer affects answers.

Acceptance criteria

  • Delete removes or tombstones the source, chunks, vectors, graph-derived records, and associated derived data according to the deletion SLA.
  • Reingest creates a traceable new version and prevents mixed old/new retrieval results.
  • Deletion and reingestion actions are authorized, auditable, and reflected in UI status.

Dependencies: SB-13, SB-17, SB-29, SB-39.

Epic E — Retrieval, Chat, and Orchestration

SB-19 Retrieve grounded document evidence

Story: As a user, I want relevant document evidence found for my question so answers can be supported by my sources.

Acceptance criteria

  • Retrieval accepts a query and approved metadata filters and searches only the authenticated user’s vectors.
  • Results include ranked chunks and complete citation provenance.
  • When Qdrant is unavailable, the service returns controlled degraded behavior rather than crashing the API.

Dependencies: SB-8, SB-17.

SB-20 Generate citation-backed answers

Story: As a user, I want document-derived claims cited so I can verify an answer against the original source.

Acceptance criteria

  • Answer output distinguishes sourced statements from inference and includes source document, page/section where available, chunk ID, and ingestion version.
  • The UI lets users inspect the cited source/chunk from the chat result.
  • When no grounded evidence is found, the answer does not fabricate a citation and communicates the limitation.

Dependencies: SB-13, SB-19; LLM provider abstraction.

SB-21 Create and continue conversations

Story: As a user, I want my conversations retained so I can continue work with relevant recent context.

Acceptance criteria

  • Chat requests create or append to user-scoped conversation and message records.
  • Conversation list and detail endpoints return only authorized history in deterministic order.
  • Raw messages and generated outputs are handled under the platform retention/privacy policy.

Dependencies: SB-5, SB-8.

SB-22 Stream chat events to the web client

Story: As a user, I want progressive answer updates so I can see useful work without waiting for the entire workflow.

Acceptance criteria

  • POST /api/v1/chat streams documented SSE events for token, citation, tool status, confirmation required, final, and controlled error.
  • Events carry conversation and trace context and have a versioned schema.
  • The UI handles reconnect/failure gracefully and never renders a tool action as completed before verified success.

Dependencies: SB-10, SB-20, SB-25.

SB-23 Route requests with LangGraph

Story: As the platform, I need policy-aware request routing so only relevant retrieval stores and tools are invoked.

Acceptance criteria

  • Workflow state includes the TRD-defined identity, conversation, trace, query, intent, context, tool, confirmation, result, and error fields.
  • Intent routing supports chat, RAG, memory, graph, tool, and composite paths.
  • Independent retrieval paths may run in parallel; evidence is reconciled before an answer is planned.

Dependencies: SB-19, SB-21, SB-27, SB-29, SB-31.

SB-24 Apply workflow policy gates and graceful degradation

Story: As a user, I want safe, honest responses when a subsystem cannot be used so a partial failure does not destroy the core experience.

Acceptance criteria

  • Policy checks run before tools or high-impact memory writes.
  • Defined failures for Qdrant, Neo4j, Mem0, provider APIs, workers, LLMs, and MCP tools follow the TRD’s degraded behavior.
  • Responses never falsely claim that an unavailable retrieval or action succeeded.

Dependencies: SB-23, SB-36, SB-38.

Epic F — Durable Memory and Knowledge Graph

SB-25 Extract candidate durable memories

Story: As a user, I want lasting preferences, facts, decisions, relationships, and goals retained when appropriate so future interactions are more useful.

Acceptance criteria

  • Candidate extraction classifies preference, fact, decision, relationship, goal, and temporary context.
  • Temporary context is not automatically persisted as durable memory.
  • Every durable write retains user, source conversation/event, timestamp, and policy metadata.

Dependencies: SB-21, SB-23; approved memory-write policy.

SB-26 Consolidate and retrieve durable memories

Story: As the platform, I need equivalent memories consolidated and relevant memories retrieved so personalization is useful without duplication.

Acceptance criteria

  • Duplicate or semantically equivalent candidates are merged or superseded with traceable provenance.
  • Memory retrieval is scoped to the authenticated user and contributes only when relevant to the request.
  • Mem0 failure permits current-turn conversation while safely skipping the durable update.

Dependencies: SB-8, SB-25.

SB-27 Let users manage memories

Story: As a user, I want to view, edit, pin, and delete my memories so I remain in control of personalization.

Acceptance criteria

  • Memory list, update, delete, and pin APIs are authorized and exposed in the Memories screen.
  • Edits and deletion update application metadata and the memory provider consistently.
  • Changes are auditable and deleted memories are excluded from future retrieval within the defined SLA.

Dependencies: SB-9, SB-25, SB-26, SB-39.

SB-28 Extract graph entities and relationships

Story: As the platform, I need entities and relationships derived from documents so explicit connections can support appropriate questions.

Acceptance criteria

  • The extractor supports the approved entity and relationship types and preserves source/provenance plus confidence.
  • Low-confidence inferred relationships are marked and are not presented as authoritative facts.
  • Entity extraction is optional within ingestion and failure does not prevent document RAG from reaching READY when graph enrichment is non-critical.

Dependencies: SB-16, SB-17; extraction-model policy.

SB-29 Resolve and query the knowledge graph

Story: As a user, I want grounded relationship answers and graph exploration when traversal adds value beyond semantic search.

Acceptance criteria

  • Entity resolution combines deterministic keys with approved similarity rules and retains merge provenance.
  • Graph queries are user-scoped and return only evidence-backed entities/relationships with confidence.
  • The UI provides a graph exploration view and handles Neo4j unavailability with a clear limitation state.

Dependencies: SB-8, SB-9, SB-28.

Epic G — External Tools and Integrations

SB-30 Establish the MCP tool boundary

Story: As the platform, I need typed external tool adapters so provider-specific APIs are isolated from domain logic.

Acceptance criteria

  • Every tool defines name, description, typed input/output schema, authorization requirement, invocation ID, and output limits.
  • Tool outputs are sanitized before reaching model context and raw provider credentials never enter prompts or telemetry.
  • Tool invocation records capture request intent, safe parameters, status, result summary, and trace ID.

Dependencies: SB-3, SB-4, SB-38.

SB-31 Connect and revoke Google accounts

Story: As a user, I want to connect or revoke Gmail and Calendar access so I control which external accounts Second Brain may use.

Acceptance criteria

  • OAuth consent requests minimum approved scopes and binds the provider account to the authenticated user.
  • Tokens are encrypted at rest, are never shown to the client, and revocation removes usable access.
  • Integration list shows connection status and scopes without exposing credentials.

Dependencies: SB-4, SB-6, SB-30; Google OAuth client and scope approval.

SB-32 Search and inspect Gmail safely

Story: As a user, I want to search and inspect my Gmail messages through Second Brain so I can use them as personal work context.

Acceptance criteria

  • Gmail search and get-message tools require an authorized connected account and user context.
  • Results are size-limited, sanitized, traceable, and accurately describe provider failures.
  • The workflow chooses Gmail only when the user request and policy permit it.

Dependencies: SB-23, SB-30, SB-31.

SB-33 Create Gmail drafts

Story: As a user, I want a draft created from approved content so I can review it before sending.

Acceptance criteria

  • The tool creates a draft only; it does not send email.
  • The user receives a clear preview/confirmation of recipients, subject, and content before execution.
  • Successful and failed draft creation are recorded with unique invocation ID and safe result summary.

Dependencies: SB-30, SB-31, SB-34.

SB-34 Manage Calendar through confirmation-gated tools

Story: As a user, I want to list, create, update, and delete Calendar events with explicit confirmation so external changes happen only when I approve them.

Acceptance criteria

  • Calendar list, create, update, and delete tools use typed schemas and validate time zones and required fields.
  • Create, update, and delete require a clear confirmation that describes the exact intended action.
  • Confirmation is bound to the proposed invocation, expires safely, and cannot be replayed for changed parameters.
  • Destructive action failures never claim success and are auditable.

Dependencies: SB-22, SB-30, SB-31.

Epic H — Async Processing, Reliability, and Audit

SB-35 Operate reliable background workers

Story: As an operator, I need asynchronous workers with resilient job semantics so ingestion and long-running tasks recover from transient failure.

Acceptance criteria

  • Workers consume Redis jobs idempotently with bounded backoff and configured retry limits.
  • Exhausted or poisoned jobs move to DEAD_LETTER with failure context safe for operators.
  • Job state transitions, attempt counts, and timing are persisted and visible via API.

Dependencies: SB-2, SB-5.

SB-36 Monitor jobs and recover failures

Story: As a user or operator, I want to see long-running job status and recover permitted failures so work is not silently lost.

Acceptance criteria

  • Jobs screen lists authorized jobs with type, status, progress/phase, attempts, timestamps, and safe error details.
  • Permitted retry/reingest controls create a new traceable execution rather than mutating history invisibly.
  • Dead-letter jobs are discoverable and operational remediation is documented.

Dependencies: SB-9, SB-35.

SB-37 Record security and activity audits

Story: As an operator, I need a defensible audit trail so I can investigate access and external actions without storing unnecessary sensitive content.

Acceptance criteria

  • Authentication, integration changes, data lifecycle actions, confirmations, and tool invocations create audit events with actor, time, target, outcome, and trace reference.
  • Audit logs avoid raw sensitive content unless policy explicitly allows it.
  • The Audit screen supports authorized filter and inspection of records.

Dependencies: SB-5, SB-9, SB-30.

Epic I — Security, Observability, and Quality

SB-38 Secure data, prompts, and external actions

Story: As a user, I need my personal data and OAuth access protected so the assistant is safe to trust.

Acceptance criteria

  • OAuth tokens and secrets are encrypted at rest and excluded from prompts, logs, telemetry, source control, and client storage.
  • All destructive actions require confirmation and externally visible operations support idempotency where practical.
  • Rate limiting and abuse controls protect LLM and integration endpoints.
  • A documented threat model covers user isolation, prompt/tool injection, credential exposure, and deletion.

Dependencies: SB-4, SB-8, SB-30.

SB-39 Honor personal-data deletion obligations

Story: As a user, I need my content and derived data deleted within a defined SLA so I can exercise control over my data.

Acceptance criteria

  • The deletion workflow identifies affected PostgreSQL, object storage, Qdrant, Neo4j, Mem0, cache, and provider-derived records.
  • Deletion completion, partial failure, retries, and SLA measurement are tracked.
  • Automated tests prove deleted data is unavailable through normal document, memory, graph, and retrieval paths.

Dependencies: SB-18, SB-27, SB-29, SB-38.

SB-40 Trace workflows end to end

Story: As an operator, I want a trace ID to follow each chat request across services so I can diagnose latency, failures, and cost.

Acceptance criteria

  • Each chat request gets a trace ID propagated through API, LangGraph nodes, retrieval, LLM, tool, and worker calls.
  • Logs and telemetry correlate safely to trace ID without leaking sensitive contents.
  • Trace detail identifies workflow path, timings, controlled errors, and tool outcomes.

Dependencies: SB-3, SB-23, SB-35.

SB-41 Publish operational metrics and dashboards

Story: As an operator, I want measurable service health and AI-quality signals so I can detect regressions before users do.

Acceptance criteria

  • Metrics include request/node/LLM latency and tokens, retrieval hits, tool success/error rate, retries, confirmations, memory duplicate/false-memory rate, and deletion rate.
  • Dashboards support service, workflow, and integration views with agreed alert thresholds.
  • Metric definitions, sampling/privacy rules, and owners are documented.

Dependencies: SB-37, SB-40.

SB-42 Build automated test coverage

Story: As an engineering team, we need layered automated tests so key behavior remains reliable as the architecture grows.

Acceptance criteria

  • Test suites cover frontend unit, backend unit, integration, agent routing/state transitions, E2E flows, security isolation, and load scenarios.
  • Critical flows cover upload-to-READY, RAG-to-citation, memory lifecycle, graph query, and Calendar action confirmation.
  • CI runs required suites and publishes actionable results.

Dependencies: SB-1; each corresponding feature story.

SB-43 Create evaluation datasets and quality gates

Story: As a product team, I need representative evaluation data and thresholds so RAG, memory, graph, and tools are not declared production-ready based on anecdotes.

Acceptance criteria

  • A representative corpus contains the TRD’s target volumes for technical documents, sanitized emails, notes, entities/relationships, conversations, and memories.
  • Evaluation suites measure retrieval recall, groundedness, citation correctness, answer relevance, memory errors, graph correctness, tool correctness, safety, latency, cost, and recovery.
  • Release thresholds and a regression policy are agreed and version-controlled.

Dependencies: SB-19, SB-25, SB-28, SB-30, SB-42.

Epic J — Voice and Production Delivery

SB-44 Support voice requests and responses

Story: As a user, I want to speak a request and receive a spoken response so Second Brain is useful hands-free.

Acceptance criteria

  • The UI captures voice input, sends it to the approved STT provider, and presents editable transcription before consequential actions.
  • Text orchestration follows the same authorization, confirmation, trace, and citation rules as typed chat.
  • TTS renders the final response with user controls and controlled failure behavior.

Dependencies: SB-22, SB-23; selected STT/TTS providers and privacy policy.

SB-45 Deploy the production architecture

Story: As an operator, I need a production deployment path so the system can scale beyond the MVP without changing its service boundaries.

Acceptance criteria

  • Deployment supports load balancing/CDN for web assets, API and worker scaling, Redis, PostgreSQL, Qdrant, Neo4j, object storage, MCP, and managed configuration/secrets.
  • Infrastructure configuration is version-controlled, environment-specific, and includes health checks, backups, and rollback procedures.
  • Production readiness documents capacity assumptions, availability target, RPO/RTO, monitoring, and incident ownership.

Dependencies: SB-2, SB-4, SB-35, SB-41.

SB-46 Prove the MVP definition of done

Story: As the product owner, I need an objective release checklist so we know when the MVP is safe and complete enough to launch.

Acceptance criteria

  • All MVP functional journeys pass end-to-end with secure sessions, document ingestion, citation-backed RAG, durable memory, graph answer, Google tools, voice, audit traces, and graceful degradation.
  • No plaintext credentials or OAuth tokens are found in approved scanning, logs, prompts, source control, or client storage.
  • Evaluation thresholds are met and architecture/API/runbook documentation is committed with reproducible startup instructions.

Dependencies: SB-1 through SB-45 as applicable to approved MVP scope.
